# SWEEP Migration Framework - Operational Monitoring & Output Reference (v5.4.0)

This reference outlines the exact visual and structured reporting outputs generated by the **SWEEP Unified Data Migration Framework** across CLI commands, real-time dashboards, background logs, and multi-tab Excel reports.

## 2. Structured Excel Reports

### 2.1 VSAM Step 03: Type Gate Report
* **Path:** `vsam/reports/<db>_vsam_03_type_gate_report_<timestamp>.xlsx` - sheets `TypeGateSummary`, `GateSummary`, `PKVerification`, `SchemaColumnDetect`, `TypeIssues`.
* **`TypeGateSummary` layout (11 columns):** `S3 file name`, `source key`, `schema`, `copybook`, `table`, `has PK?`, `PK Columns`, `is PK valid`, `has schema_col?`, `schema_col`, `Full S3 URI`.

| Column | Description | Example |
| :--- | :--- | :--- |
| `S3 file name` | Latest discovered file basename for the source | `FDICSWP_FDIC_VSAMKORG_FLAT_20260901.csv.gz` |
| `source key` | `<company> \| <source file>` | `FDIC \| VSAMKORG` |
| `schema` | Target schema(s) the source maps to | `bss01104, bss01112` |
| `copybook` | Mapped copybook name | `VSAMKORG` *(or `NO_COPYBOOK`)* |
| `table` | Target destination table | `vsamkorg` |
| `has PK?` | Whether a valid primary key was established | `YES` / `NO` |
| `PK Columns` | Primary key column list | `korg, account_id` |
| `is PK valid` | Uniqueness check outcome | `YES` / `NO` |
| `has schema_col?` | Whether a schema (korg) column was detected | `YES` / `NO` |
| `schema_col` | The detected schema column | `b_korg` *(or `NO_KORG`)* |
| `Full S3 URI` | Full path of the profiled file | `s3://migration-bucket/vsam/FDICSWP_...` |

The `GateSummary` sheet adds per-source detail: `company`, `source_file`, `version_date`, `is_latest_version`, `rows_checked`, `status` (`PASS` / `BLOCKED` / `EMPTY_NO_DATA` ...), `pk_type`, `schema_col_is_pk`, `schema_map`, `type_issues_count`, `issues`.

### 2.1b VSAM Step 02: Inventory Report and Column Mapping
* **Path:** `vsam/reports/<db>_vsam_02_inventory_report_<timestamp>.xlsx` - sheets `Summary`, `FileInventory`, `LatestFileHeaders`, **`ColumnMapping`**; the same mapping is written to `vsam/outputs/vsam_02_column_map.csv`.
* **`FileInventory`** adds: `key source` (`COPYBOOK`, `OVERRIDE`, `KORG_SHEET`, `COPYBOOK_UNMAPPED`, `NONE`), `candidate key (not applied)`, `mapped columns`, `review columns`, `unmapped columns`.
* **`ColumnMapping`** (one row per S3 header, plus one row per copybook column that is not in the file):

| Column | Description |
| :--- | :--- |
| `source_company`, `source_filename`, `latest_filename`, `copybook_name` | which source / file / copybook the row belongs to |
| `header_position`, `header` | position and normalised name in the S3 file (`0` / blank for `COPYBOOK_ONLY` rows) |
| `table_column` | the column name used in the PostgreSQL table (`--tbl-col headers` = the header, `copybook` = the mapped copybook name) |
| `copybook_field`, `copybook_col`, `pic`, `usage` | the matched copybook field as written / normalised, with its PICTURE and USAGE |
| `copybook_type`, `pg_type` | datatype of the copybook column and the type used for the table (`text` for unmapped headers) |
| `is_key` | `YES` when the matched copybook column is part of the copybook key |
| `score`, `confidence`, `status`, `method` | similarity 0-1; `EXACT`/`HIGH`/`MEDIUM`/`STICKY`/`OVERRIDE`/`UNMAPPED`; `ACCEPTED`/`REVIEW`/`UNMAPPED`/`COPYBOOK_ONLY`; how it was matched (`OVERRIDE`, `STICKY`, `EXACT_NAME`, `ALGORITHM`, `NONE`) |
| `tbl_col_mode` | `headers` or `copybook` |

Rows with status `REVIEW` or `UNMAPPED` are the ones to check; correct them in the `column_overrides` sheet of `vsam_master_overrides.xlsx` and re-run Step 02.

### 2.2 VSAM Step 06: Ingestion Load Report
* **Path:** `vsam/reports/<db>_vsam_06_load_data_report_<timestamp>.xlsx` (plus `vsam/outputs/vsam_06_load_log_<run_id>.csv`)
* **Sheets:** `LoadSummary` (Master File Execution), `SchemaBreakdown` (Cross-Tabulation Matrix) and `RunOverview` (run id, task / success / failed counts, rows loaded and skipped, workers).

#### Sheet 1: `LoadSummary` (17 Columns)
1. `s3 filename`: Source S3 file basename.
2. `tablename`: Target PostgreSQL table.
3. `copybook`: Copybook name or `NO_COPYBOOK` if unmapped.
4. `korg column`: Mapped schema segregation column or `NO_KORG`.
5. `total recs`: Total raw records present in source file.
6. `loaded recs`: Total records successfully inserted/upserted.
7. `skipped recs`: Records skipped due to PK violations or duplicate keys.
8. `records loaded in mapped schema`: Records per explicitly mapped destination schema, e.g. `bss01104 = 20, bss01112 = 34` (blank when none).
9. `records loaded in unmapped schema`: Records per non-mapped existing schema, same format (blank when none).
10. `records loaded in bcs schema`: Records routed to the fallback `bcs` schema.
11. `load %`: Percentage of records loaded into mapped schema: `(mapped_loaded / total_records) * 100`.
12. `has PK?`: `YES` if table has deployed PK constraint; else `NO`.
13. `PK columns`: Primary key column names used for upsert.
14. `skipped/failed reason`: The error message or reason, up to 1,000 characters (longer text ends with `...[+N chars]`).
15. `duration`: File streaming and load duration in seconds.
16. `status`: `SUCCESS`, `SKIPPED`, or `FAILED`.
17. `full s3 uri`: Complete S3 object URI.

#### Sheet 2: `SchemaBreakdown` (Pivot Matrix)
Cross-tabulates rows against schemas:
- **Rows:** `s3 filename` and `tablename`.
- **Columns:** Dynamic destination schemas (`bcs`, `bss01104`, `bss01105`, `bss01112`, etc.) + `Total` column.
- **Intersections:** Total records committed to that specific schema for that file.
- **Summary:** Bottom `TOTAL` row consolidating all schema commits.

### 2.3 VSAM Step 07 & Oracle Step 08: Validation Reports
* **Oracle:** `oracle/reports/<db>_oracle_08_validate_report_<timestamp>.xlsx` (10 tabs: `Executive_Summary`, `Schema_Comparison`, `Table_Comparison`, `Column_Comparison`, `Constraints_Comparison`, `Index_Comparison`, `Sequence_Comparison`, `Views_and_Triggers`, `Row_Count_Audit`, `Discrepancies`). The step exits `0` only for a full-parity verdict.
* **VSAM:** `vsam/reports/<db>_vsam_07_validate_report_<timestamp>.xlsx` (5 tabs: `FileReconciliation`, `RowCounts`, `ColumnAudit`, `TypeAudit`, `PKAudit`). The step exits `1` when files are not loaded, columns are missing or types mismatch.

Includes side-by-side reconciliation of:
- `Executive_Summary`: High-level counts, pass/fail status, and audit KPIs.
- `Schema_Comparison`: Schema object parity.
- `Table_Comparison`: Table presence, partition hierarchies.
- `Column_Comparison`: Column datatypes, lengths, precision, nullability.
- `Row_Count_Audit`: Exact `COUNT(*)` vs `sweep_ctl.load_log` vs Oracle catalog metadata.

## 3. PostgreSQL Audit Tables (`sweep_ctl.load_log`)

File loads are recorded in `sweep_ctl.load_log` (created by `sweep_meta.sql`):

```sql
CREATE TABLE sweep_ctl.load_log (
    uri             text PRIMARY KEY,        -- Oracle: the file URI; VSAM: '<uri>#<schema>' (one row per destination schema)
    target_schema   text NOT NULL,
    target_table    text NOT NULL,
    size_bytes      bigint DEFAULT 0,
    loaded_rows     bigint DEFAULT 0,
    seconds         numeric DEFAULT 0,
    rows_per_sec    numeric GENERATED ALWAYS AS (
        CASE WHEN seconds > 0 THEN ROUND(loaded_rows / seconds, 2) ELSE 0 END
    ) STORED,
    file_format     text DEFAULT 'gzip',
    worker_id       int DEFAULT 1,
    status          text DEFAULT 'SUCCESS',  -- 'SUCCESS' or 'FAILED'
    message         text,                    -- error text for FAILED rows; VSAM SUCCESS rows: source=<co|file>;snapshot=<version>
    loaded_at       timestamptz DEFAULT now(),
    s3_last_modified text,                   -- S3 object metadata as loaded (UTC ISO 8601, ETag without quotes, bytes);
    s3_etag          text,                   -- a file is 'already loaded' only while all three still match S3
    s3_size          bigint
);
```

* **Oracle track:** the `SUCCESS` row is inserted in the *same transaction* as the data, so a row exists if and only if the data was committed.
* **VSAM track:** the `SUCCESS` rows (one per destination schema) are written in the *same transaction* as the data as well. `FAILED` rows carry the error in `message`.
* `sweep_ctl.load_rejects` holds the rejected rows of both tracks: `uri`, `target_schema`, `target_table`, `row_no`, `reason`, `detail`, `row_data` (jsonb), `file_status` (`LOADED`, or `FILE_FAILED` for the sample kept from a rolled-back file), `rejected_at`.
* Run-level history lives in `sweep_ctl.load_audit`.

## Step 06 reject reporting and end-of-step summary (v5.4.0)

`oracle/reports/oracle_06_load_data_*.xlsx` and `vsam/reports/*_vsam_06_load_data_report_*.xlsx` have the sheets `Reject_Summary` (file, table, reason, detail, row count) and `Rejected_Rows` (record number, reason, detail, row as JSON, up to 10,000 rows; all rows are kept in `sweep_ctl.load_rejects`).
